# 业务逻辑通用模式

来自近期跨项目实践，结合本项目 Handler / Module / PlayerHelper 适配。详细 API 见 [ai-coding.md](ai-coding.md)，专题见 [business-patterns/README.md](business-patterns/README.md)。

## 共性原则

- 先复用已有校验、资源、条件、事件、保存和登录链路；新增类型不能绕过旧系统的资格、限购、资源与归属校验。
- 分清条件判断、状态推进和协议展示。已完成、已领取、可展示、可开启下一阶段、红点是不同语义。
- 高频登录、事件、定时回调先做内存、窗口、开关等低成本过滤，再访问存储或扫描集合。
- 同一流程复用已加载对象，通过参数下传；不要反复读取同一份数据或用旧快照覆盖新状态。
- 查询接口包含懒重置/补偿时，也属于状态变更，须纳入本项目保存链路并验证重载结果。
- 写入口独立核算当前周期并幂等重置；不能假设客户端已经调用查询页。先处理旧周期计数，再更新周期标识，避免把旧计数固化到新周期。
- 奖励、扣费、状态位、事件、通知与回包形成完整闭环。中途失败要明确回滚/补偿/重试策略，不能把玩家串行执行误当作跨系统事务。
- 旧数据增量迁移、补发、重登恢复必须幂等；清理旧字段/协议要晚于实际兼容窗口结束。

## 本项目落点

1. Handler 解析 Protobuf、获取玩家、校验并调用 Module/Helper，最后构造响应。
2. 玩家队列内通过 `player.getModule(...)` 读写模块；外部回调回投队列，异步操作用 `AsyncUtils.await(...)`。
3. 资源检查、扣除、发放使用 `PlayerHelper`，批量成本选用匹配的批量重载；返回奖励按协议契约加入响应。
4. 常规 Module 交由框架保存，独立表走 `DbEntity`；确认生命周期保存和异常窗口，不能为了套用经验普遍增加手动保存。
5. `player.fireAndHandleEvent(...)` 处理玩家事件，参数顺序与类型须有契约；事件只在对应业务成功后触发，重试避免重复联动。
6. 条件判断复用 Condition 多态体系；详见 [systems/condition-system.md](systems/condition-system.md)，不往公共 Helper 堆特判。

测试至少覆盖真实入口、失败分支、重复调用及相关状态恢复。保存类缺陷要验证保存完成后的新对象，不能仅断言协议回包。
