## 通用请求链路

| 阶段 | 本项目责任边界 | 必须避免 |
|---|---|---|
| 协议边界 | Handler 解析请求、从可信连接确定玩家、核实输入和归属 | 使用客户端 playerId 或奖励数量作权威数据 |
| 低成本校验 | 功能开关、资格、活动窗口、参数范围；复用已有通用校验链 | 新类型通过特判绕过旧资格/限购链路 |
| 获取状态 | 玩家队列内通过 `player.getModule(...)` 获取对象，下传复用 | 在同一调用链反复加载对象或用旧副本覆盖新状态 |
| 统一周期 | 查询和写入口均核对周期；重置旧计数后再设置周期标识 | 假设客户端先打开页面；旧计数累加后覆盖新时间 |
| 业务推进 | Module/Helper 处理资格、批量成本、奖励和领取状态 | 条件函数顺手发奖；把部分成功当整体成功 |
| 保存与恢复 | 常规 Module 纳入框架保存；独立表遵循 DbEntity，明确异常窗口 | 认为内存正确或回包成功就已落库 |
| 展示 | 明确全量/增量、通知与响应分工，返回实际业务结果 | 发奖预览冒充实际发放结果 |

## 条件、状态与展示分开

条件回答“能否执行”，状态转换回答“执行后是什么”，展示回答“接收方应看到什么”。已完成、已领取、可显示、可开下一阶段和红点是独立概念。可领奖由服务端状态判断，不能由客户端传来的按钮状态决定。

单玩家队列保证其负责范围内串行；外部回调先回投队列，异步等待用 `AsyncUtils.await(...)`。跨玩家、跨节点或外部系统仍需明确一致性策略，不能把队列当分布式事务。

## 获取、初始化与旧数据

复用既有 Module 的初始化、反序列化与登录恢复链路。新增默认值、懒升级、缓存回填应集中在有明确职责的入口，不能散落多个 Handler。登录恢复核对旧周期收尾与新周期初始化顺序；补偿、重试和迁移必须幂等。常规 Module 与独立表的保存方式不得互换。

查询若会懒重置、补偿或重算持久状态，就包含副作用，须跟踪真实保存完成；写入口也独立防御重置。测试用新对象从存储冷读，不读取同一 Player 内存就宣称保存通过。

## 高频路径与资源闭环

登录、红点、事件、定时回调先做内存/开关/窗口过滤，再 IO 或扫描；复用已加载对象，避免每个子方法重新读取。批量消耗采用适合的 `PlayerHelper.delResources` 重载并确认整体检查语义；批量 API 名称本身不保证跨模块原子性。

奖励、扣费、领取位、事件、日志、通知与回包共同组成闭环。失败需要可判定的回滚/补偿/重试策略；日志携带玩家、轮次、操作和失败原因。发布前核实新旧版本混跑和回写路径，不能用“发版后自然稳定”代替恢复方案。

## 反例与验收

| 反例 | 修正 | 必须覆盖的场景 |
|---|---|---|
| 页面查询才 reset，直接购买沿用旧次数 | 写入口复用幂等周期校正 | 未先查询直接写、边界日、重复写 |
| 已领奖立刻从所有列表删掉 | 展示策略按功能规则独立处理 | 已领展示、下一阶段、重新登录 |
| 返回奖励列表但未修改资源 | 返回公共发奖入口的实际结果 | 资源增量、领取位、通知与响应 |
| 为测试改公共保存框架 | 使用现有保存契约与隔离 fixture | 保存完成后新对象重载 |
