# 活动系统模式

## 本项目落点与生命周期

活动实现位于 `cn.game.games.net.game.module.activity`：`ActivityBase` 定义共同能力，`PlayerActivityBase` / `PlayerActivityManager` 管个人活动，`GlobalActivityManager` 及其实现管全服活动，`ActivityModule` 接入玩家生命周期，`ActivityHandler` 承担协议边界。具体类型由现有 `ActivityFactory` / `ActivityType` 链路创建。

`ActivityModule.onLogin()` 调用 `checkAndOpenActivitys(player)`、`endTimeTask()`、`destroyTimeTask()`；加载/过期检查还涉及 `checkExpired()`。这些是当前实现的入口，不把其他项目“先收尾后初始化”的调用顺序未经核实写成本项目事实。新增周期逻辑仍须保证旧周期结算不被新初始化覆盖。

| 阶段 | 必须明确 | 常见遗漏 |
|---|---|---|
| 开放 | 全服/个人窗口、资格、功能开关、时区和周期标识 | 只判断配置存在就开放 |
| 初始化 | 活动 ID/实例/周期、首次数据、旧数据兼容 | 每次打开页面重置旧奖励 |
| 进行 | 正式入口、任务/排行联动、展示与可操作状态 | 页面能显示但正式请求无资格检查 |
| 结束 | 截止时点、结算、邮件、剩余奖励/道具回收 | 直接删数据导致未领奖丢失 |
| 销毁 | 结算完成后清数据、取消监听/定时任务 | 重登重发结算或残留回调 |

协议 `ActivityState` 为 NONE / VIEW / START / CLOSE。CLOSE 的协议注释允许“仅查看或领奖”等功能行为，因此不能把所有关闭态一律当作不显示或禁止领奖；活动结束时间与销毁时间不同，按本活动规则确定。

## 接入步骤

1. 确定活动类型和时间口径，再设计玩家/全服数据归属及保存契约。
2. 接入既有创建、登录恢复、结束和销毁链路；不能只在首页请求里初始化。
3. 明确每个周期应保留、重置、结算和补偿的字段，使用幂等周期标识；中断后先恢复未完成结算再覆盖旧数据。
4. Handler 只处理协议边界，活动资格、状态推进与结算归活动实现/Manager；复用任务、奖励、排行、邮件能力。
5. 对任务、红点、图标、奖励、结束后领奖窗口逐项核对，不以“能打开页面”作为全链路完成。

## 性能与恢复

登录和定时入口先检查功能、活动窗口及资格，再加载或扫描；同一流程复用活动对象。全服/跨服活动和玩家活动的执行域不同，玩家队列不能替代全服互斥。时间推进、结算与补偿须可重复调用，写清失败窗口与恢复责任。

## 反例与测试

| 反例 | 修正 | 断言 |
|---|---|---|
| 初始化新周期后才读取旧奖励 | 收尾依据在覆盖前保存/处理，复用现有生命周期 | 跨多个周期与中断重登不丢奖、不重发 |
| 过期即删除全部数据 | 区分 end 与 destroy，先完成结算/领奖窗口 | CLOSE 可见性符合功能规则 |
| 登录和首页各写一套初始化 | 统一幂等入口 | 登录、直接协议、重复登录结果一致 |
| 活动关闭仍残留红点 | 总入口/实例判定使用同一资格与状态规则 | 开放、关闭、未解锁、销毁均正确 |

覆盖首登、直接写请求、边界时刻、离线跨期、重复结算、保存后恢复、任务/排行/邮件联动及旧数据缺省。
