# 任务系统模式

本项目采用 `QuestModule` / `Quest` / `QuestHelper` 与 Condition 体系。任务配置由 `QuestConfig` / `QuestManager` 提供；先阅读 [条件系统](condition-system.md)，不从外部项目复制任务模型或全局扫描方案。

## 接入与状态

| 能力 | 当前入口 | 设计关注点 |
|---|---|---|
| 开放任务 | `QuestModule.open(...)`、`checkOpen(...)` | 前置、分组、周期、通知与晚开启补判 |
| 更新进度 | Condition 监听 PlayerEvent，Module 更新 Quest | 事件参数、增量/累计语义、重复事件 |
| 领奖 | `QuestModule.receive(...)`、`QuestHelper.canReceive(...)` | 完成与已领分离、资格、实际奖励、重复请求 |
| 后续推进 | finish / 新任务开放链路 | 完成即开还是领奖后开，由功能明确 |
| 红点与展示 | `QuestModule.hasRed()` 和对应协议 | 已完成未领取、已领是否保留、页签过滤 |

不能把“已完成”“已领取”“下一阶段开放”“应显示”写成同一个布尔值。是否移除已领任务、是否自动开启下一段必须有规则依据，不凭 UI 推断。

## 新任务步骤

1. 选择已有日常、主线、活动或专属任务体系，确认配置组、目标、条件模式、周期及进度单位。
2. 补具体 Condition 实现/映射及真实业务事件生产点，不只加配置。
3. 明确开放、进行、完成、领取和关闭的转换，以及客户端全量/增量展示。
4. 对 countType=1/2 新开启任务使用当前值补判；countType=0 的“接取后计数”不能追溯之前行为。
5. 阶段推进只负责专属规则，通用判定、资源和事件继续复用现有入口。
6. 核实保存链路和重登恢复，批量领奖说明部分失败/幂等语义。

## 正反例

| 错误 | 正确落点 | 回归要求 |
|---|---|---|
| 仅在打开任务页扫描最新进度 | 真实动作事件更新，晚开启时按类型补判 | 不打开页面也正确推进 |
| 已达到等级后新任务只能等再次升级 | 复用 Condition 的实时值获取 | 开启后立即可完成 |
| 每个活动复制一份条件分支 | 共享 Condition，专属模块只处理阶段/展示 | 同条件跨功能结果一致 |
| 已领奖直接删列表导致前端丢展示 | 独立定义保留/隐藏规则 | 已领取显示与下一段互不混淆 |
| 收到重复事件再次发奖 | 事件推进与领奖副作用分离、领取幂等 | 重复事件/请求不重复资源 |

## 性能与验证

高频动作只投递必要事件，不在生产点扫描全部任务。复用本轮已读取的 Quest/Module，提前过滤类型、功能和周期。验证事件 → 进度 → 完成 → 领奖 → 展示，以及资源不足、非法 ID/归属、阶段边界、晚开启、跨天与保存后新对象恢复。
