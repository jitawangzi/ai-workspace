# 红点开发模式

## 语义与真源

红点是当前业务状态的派生结论：可领取、免费/关键可购买、可操作、新内容未读。先写清亮起与消失条件；不要给所有普通可购买商品都加红点。能从任务/奖励状态推导时不重复持久化；已读/未读需要记忆时才保存阅读游标或状态，并核实保存链路。

## 本项目已核实的协议与入口

| 场景 | 协议及实现 | 保持的契约 |
|---|---|---|
| 玩家功能 | `PlayerRedPointRequest_01000075.type` → `PlayerHandler.red` → 功能判定 | type 是 InitialUI ID；响应 `PlayerRedPointResponse_01000076.isRed` 按请求下标一一对应 |
| 活动 | `ActivityRedPointRequest_11000003.ids` → `ActivityHandler.redPoint` → `ActivityBase.hasRed()` | ids 是 Activity ID；响应 `ActivityRedPointResponse_11000004.isRed` 保持长度与顺序，不存在实例返回 false |
| 任务 | `QuestModule.hasRed()` | 复用可领取判定，不保存另一份可领标志 |

当前协议是 `repeated bool`，不是位图。新增明细位图只作为未来确有需求的协议设计选项，不能直接把现有响应换成 bit 值。

## 推荐分层

- 总入口：Handler 按请求列表取结果并维持下标契约，只做编排。
- 模块聚合：已有活动入口 `hasRed()` 或任务入口，聚合本模块多个来源。
- 单一原因：如“有可领任务”“有未读记录”“有免费次数”，每个小函数只解释一种语义。

已有 PlayerHandler 中的分支仅在本功能触达范围内扩展，不为落实分层规则全量重构旧代码。模块内部若需组合多个来源，可布尔短路；确需明细时使用稳定命名/新协议字段，记录每一位语义且不重用旧位。

## 实现顺序

1. 明确亮/灭条件、模块粒度、总入口是否参与、关闭后领奖窗口是否仍提示。
2. 先做空对象、功能开放、活动状态、紧急开关、玩家资格/图标可见性等低成本判断，再 IO 或扫描；不能照搬“所有 CLOSE 都不亮”，按活动剩余领奖规则处理。
3. 从真实状态计算，复用上游已加载的对象，通过参数下传；不要在每个原因函数重复读存储。
4. 按原因拆分并聚合，接入当前总入口，保持请求/响应顺序、缺失项 false 及数量一致。
5. 动作成功后再计算新状态，领取/阅读/购买/活动切换后的红点与协议一致。

## 示例与反模式

以下为语义伪代码，函数名需映射为具体模块已存在的 API：

```text
若功能不可见，返回 false
复用当前活动/任务对象
返回“完成且未领取” 或 “存在游标之后的新记录”
```

| 反例 | 后果 | 修正 |
|---|---|---|
| 仅返回命中的 true，跳过 false 项 | repeated bool 与请求 ID 错位 | 每个请求 ID 都追加一个结果 |
| 为可领奖红点另存一个 bool | 领奖状态与红点漂移 | 从领取状态派生 |
| 未读内容仅看内存布尔 | 重登重复红点 | 明确保存阅读游标并冷重载验证 |
| 总入口重新写全部业务判断 | 与模块资格/周期分叉 | 调用模块入口和单一原因判定 |
| 异常无日志直接 false | 真实故障伪装成没红点 | 按约定降级并至少 warn，带玩家/活动和异常对象 |

## 日志与测试

正常高频路径避免大量 info，异常记录必要上下文与堆栈；允许返回 false/0 的降级必须是已明确的业务行为，不能吞掉所有失败。

回归覆盖亮起 → 动作成功后熄灭、重复查询无副作用、未解锁、活动开放/关闭/销毁、未读游标、多个/重复/不存在 ID、请求顺序、总红点与页内状态一致。若未来引入位图，再补旧位不变和总入口参与规则；保存类红点验证冷重载，不仅检查回包。
