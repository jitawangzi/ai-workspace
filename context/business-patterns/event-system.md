# 事件系统模式

## 适用与分层

事件用于一个动作引发多个系统联动，例如登录、升级、完成任务与跨天。单一消费者、需要立即返回结果或强顺序的局部步骤优先直接调用 Module/Helper，不为解耦形式拆出隐蔽调用链。

本项目玩家事件入口是 `player.fireAndHandleEvent(EventTypeEnum, Object...)`，由 `cn.game.games.core.event.PlayerEventBus` 与 `PlayerEvent` 承接；服务器事件另有 `ServerEventBus`。不要复制外部项目的事件框架或任务队列模型。

| 层 | 职责 | 不应承担 |
|---|---|---|
| 业务生产点 | 成功发生动作后发布已定义事件及最小参数 | 扫描所有消费者、在失败请求中发成功事件 |
| 事件契约 | EventTypeEnum、参数顺序/类型/单位、时点 | 模糊 Object 数组、把增量和累计值混用 |
| Module / Condition 消费者 | 只订阅自身事件，过滤相关参数，推进自身状态 | 重复扣费/发奖、重新加载上游已拿到的对象 |
| 生命周期 | 初始化/注册、卸载/销毁时取消监听 | 重登重复注册、销毁后残留监听 |

## 新事件接入

1. 确认已有事件能否表达事实，列出所有消费者及参数契约；新增类型不是仅加枚举。
2. 在真实动作成功点投递，明确回滚/重试是否会重发；消费涉及副作用时使用业务幂等约束。
3. 玩家事件在所属队列处理。外部异步回调先回投队列，不能把可变 Player 交给不受控线程直接修改。
4. 检查监听注册/注销与登录、模块加载、活动销毁的实际时序。
5. 按事件类型和低成本条件先过滤，再访问存储或计算；事件参数传已有数据，避免全量扫描与重复加载。

## 示例契约

`EventTypeEnum.LevelUp` 的消费者使用资产经验类型与新等级，需区分玩家经验、VIP 经验等；不能只看到 LevelUp 就推进所有等级任务。`NewDay` 与 `NewDay5` 分属自然日和 05:00 业务日，不因都叫跨天而互换。具体定义与生产点见 `EventTypeEnum`、`PlayerHelper` 和对应消费者。

## 正反例与验证

| 反例 | 修正 | 回归 |
|---|---|---|
| 请求刚进入就发“已领奖”事件 | 发奖与状态推进成功后再发，明确补偿窗口 | 失败不增长进度，重试不重复增长 |
| 每个消费者自行猜 params 下标 | 在事件契约记录类型/顺序并核对生产点 | 类型、数量、过滤字段错误能被发现 |
| 登录再次注册旧监听 | 复用现有生命周期并注销失效监听 | 重登后一次动作只被消费一次 |
| 高频事件先全表读再判断活动 | 先窗口/开关/玩家资格过滤 | 关闭活动不访问昂贵链路 |

测试从真实生产入口验证事件到条件进度、状态推进、奖励/展示的联动；直接手工改进度只能作 fixture，不能替代事件 Act。
