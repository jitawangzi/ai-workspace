# 编码规范 (Coding Style)

本文件采用**两层结构**：

1. **通用编码与维护规则**：适合跨项目复用的方法论
2. **当前项目适配规则**：仅适用于本项目当前架构、工具链与基础设施

这样做的目的，是在不额外增加 context 文件数量的前提下，逐步把“可迁移规则”和“项目绑定规则”分层沉淀。

---

## Part A. 通用编码与维护规则

本部分应尽量保持跨项目稳定，可作为未来进一步抽离通用规则文件的基础。

### A1. 变更方式：外科手术式精准修改

- **禁止全局重构**：严禁在未获得明确指令的情况下，对已有稳定方法进行重命名、提取或逻辑重写。
- **最小化干扰**：所有修改应以“增量”为主；如果需要注入逻辑，优先使用 Hook、局部扩展或在原有流程的明确位置追加。
- **保护不相关代码**：修改时必须确保不影响文件中其他不相关的业务逻辑、导入项及注释。
- **禁止追溯式整顿旧代码**：当前规范默认约束**本次新增代码**与**本次为实现需求而直接修改的代码**。对于历史遗留但本次未被需求直接触达的旧代码，即使它不完全符合当前注释、时间 API、命名或结构规范，也不要为了“顺手规范化”而改动。
- **旧代码例外条件**：只有在以下情况才允许一起调整旧代码：1）用户明确要求清理旧代码；2）旧实现已经直接阻塞当前功能正确性；3）不修就会把本次新增逻辑落到错误语义或错误链路上。除这些情况外，默认保持旧代码原样。
- **禁止借功能开发改底层框架/基础设施**：在实现单个业务功能或修复业务问题时，严禁顺手修改底层通用框架、基础设施、加载主链路、通用容器或跨模块共享机制（如 Excel 加载框架、统一协议基础设施、通用缓存框架、公共持久化主链路），除非用户明确要求，或已确认当前问题根因就是该基础设施缺陷。
- **判定标准**：如果一个改动会影响多个功能、多个模块或整条公共主链路，而不仅仅是当前业务功能本身，就应默认视为“底层框架/基础设施修改”，不能在常规业务实现中直接进行。
- **优先策略**：优先通过业务层局部实现、功能内兼容处理、已有扩展点、VO / Getter / Hook 扩展来落地需求，不要为了单个功能去改底层公共行为。

#### A1.1 遗留系统增量扩展安全规范 (Brownfield Extension Safety)

在已有成熟业务系统（如礼包系统、活动系统、商店系统、战令系统）上新增类型、配置 ID 或分支时，必须遵守以下三条铁律：
1. **零旁路原则 (No Bypass)**：必须严格复用老系统既有的通用前置校验链（如限购校验、资格校验、支付前置校验等），严禁使用简单特判（如 `if (type == 45)`）静默绕过公共防御。
2. **副作用持久化闭环 (Side-Effect Persistence Closure)**：任何方法（尤其是 `GET` / `INFO` / `OPEN` 等查询展示类接口）中一旦包含状态变更（懒重置 Lazy-Reset、红点重算、补偿发放），必须通过宿主既有持久化机制形成闭环，并验证保存后重新加载的真实状态。自动保存的 Module 应确认字段纳入保存链路与保存时机；独立表按其显式写入契约执行，不能把显式 save 当作所有项目的统一要求。严禁只凭内存或回包正确认定已保存。
3. **写操作防卫性双重自愈 (Defensive Reset on Mutation Entry)**：在购买、扣费、领奖等写操作入口处，必须具备防卫性自愈校验（强制以当前时间核算周期并执行幂等重置），严禁假设上游客户端一定调用过查询接口，严禁在未经重置校验的脏数据上累加并覆写时间戳！

### A2. 注释与设计意图沉淀规则

注释按**信息的作用范围**组织在对应位置：整体设计写在代码单元头部；调用契约写在方法或接口文档；执行意图与局部原因写在对应代码附近。以下规则适用于本次新增或直接修改的代码。

- **注释语言（所有任务强度均适用）**：以中文注释为主，使用中文成句；可以夹杂英文术语、类名、方法名、参数名及 `@param` / `@return` 等文档标签，但不得出现整句、整段英文注释。此要求覆盖类头、JavaDoc、行内与块注释、TODO / FIXME，以及测试代码中的注释。

#### A2.1 整体设计意图 (类、模块与组件头部)

- **适用判定**：承担独立职责边界、统一决定一组行为策略，或维护跨方法／跨调用约束的代码单元，必须说明整体设计意图（职责边界、核心机制及其理由）。
- **豁免判定**：仅承载数据或直接转发调用，且无额外隐性约束的代码单元，可仅做简短职责说明。
- **依据要求**：设计理由应基于已确认的需求、设计决策或可核实的约束；无法确认时应查证，不得编造架构背景或把推测写成事实。完整方案留存设计文档，代码注释仅保留理解和维护所必需的摘要。

#### A2.2 接口与方法调用契约

- **非继承/实现方法**必须包含文档，说明核心作用，并逐一明确参数与返回值的具体含义；
- **调用契约**：若调用前必须满足特定前提（如必须持有特定锁、特定生命周期阶段），或调用后产生关键结果与副作用（如异步落库、缓存驱逐、状态机流转），必须显式注明调用边界与约束；
- **继承或实现的方法**：已有明确调用契约时，复用其文档，避免重复；缺少可复用的契约说明时，仍须补充必要文档。存在调用者或维护者必须了解的实现特有约束时，应补充说明，但补充说明不得用于合理化违反上层契约的实现。

#### A2.3 执行意图与局部原因 (方法内部)

- **执行意图 (空行分段)**：包含多个独立业务或技术步骤的方法，按步骤以空行分段；每段首行说明具体目的（What），必要时说明处理范围或边界。
- **局部原因 (Local Why 判定标准)**：当代码的正确理解或修改依赖于命名、类型和直接执行过程未能表达的约束时，必须在相关代码附近说明原因。说明实际约束或设计取舍，以及当前写法要避免的问题或保证的性质；不得为满足格式编造风险。
  *（历史兼容、执行顺序、边界自愈、性能权衡等仅为常见示例，不构成适用范围限制；未列出的情形按此判定标准执行）。*
- **简单方法豁免**：纯取值、赋值或直接委托等简单方法无需强行分段；但只要存在上述隐性约束，即使只有一行也必须说明原因。
- **严禁项 (Forbidden)**：
  1. 严禁使用连续数字编号（如 `// 1.`）或机械步骤标签（防止需求插入变更引发版本控制 diff 级联污染）；
  2. 严禁语法直译，严禁“处理数据”、“避免问题”、“提升性能”等无法提供有效信息的空话套话；
  3. 严禁在注释中包含任何 AI 代理工具名、模型名或工具前缀（如 `Codex:`、`Claude:`、`Cursor:`、`Copilot:`、`Gemini:` 等）；代码与注释必须呈现为专业人类工程师的产出，不得留存任何 AI 工具标记或自我标榜。

#### A2.4 注释合格度参考标准 (正反例校准)

| 示例注释 | 判定 | 具体约束与影响剖析 |
|---|---|---|
| `// 创建集合并遍历数据` | ❌ 违规 | 语法直译，未增加任何业务或技术目的信息 |
| `// 校验订单是否仍允许取消` | ✅ 合格 | 准确表达了执行段落的具体业务目的 (What) |
| `// 防止并发问题` / `// 提升性能` | ❌ 违规 | 笼统空话，未说明具体约束与要保证的性质 |
| `// 获取锁后重新读取状态，避免按等待期间已失效的状态执行取消` | ✅ 合格 | 明确指出了隐性约束、具体设计取舍与要避免的问题 (Why) |
| `// Codex：FINISHED/CLAIMING重试也收口派生索引...` | ❌ 违规 | 包含 AI 工具/模型名称前缀，属于非专业的工具水印与代码噪音 |
| `// FINISHED/CLAIMING重试也收口派生索引，不能只依赖运抵时出池` | ✅ 合格 | 直接客观陈述隐性约束与技术原因，专业干净 |

#### A2.5 属性与常量注释

- 类或模块级属性与常量必须配有注释，说明其业务或技术含义；存在单位、有效范围或特殊值语义时，必须一并说明。

#### A2.6 修改原有代码时的注释与同步维护规则

- **修改他人原有代码**：若修改的是他人原有类或逻辑，注释中说明修改原因，若需署名必须使用真实人类作者名（严禁用 AI 工具名充当作者）；若当前类由同一作者创建并持续维护，则无需重复署名，写清逻辑变更点即可；
- **严禁 AI 工具署名与标记 (No AI Signatures / Tool Watermarks)**：严禁在任何注释、JavaDoc、TODO、FIXME 或说明文字中包含任何 AI 代理工具名、模型名或工具前缀（如 `Codex:`、`Claude:`、`Cursor:`、`Copilot:`、`Gemini:`、`AI generated` 等）；
- **严禁包含日期**：日期信息统一由版本控制系统记录；
- **同步更新约束**：调整职责、调用契约或实现约束时，必须同步更新受影响的注释；同一背景在主要维护位置说明，其他位置仅补充必要信息或引用。

### A3. 日志与错误处理

- **异常必须记录日志（所有任务强度均适用）**：每个捕获异常的处理分支都必须记录日志；即使异常可以忽略、允许降级或重试，或者后续会继续抛出，也至少使用 `warn`，严重失败使用 `error`。不得以“预期异常”“不影响主流程”或“上层可能记录”为由省略，也不能仅用 `debug` / `info` 代替。
- **保留定位信息**：日志应说明失败操作、必要的业务上下文及后续处理（如忽略、回退、重试或重新抛出），并将异常对象传给日志 API，保留堆栈与原因链；只记录 `e.getMessage()` 不足以替代异常对象。
- 关键分支、关键失败点、关键状态流转点，应补充必要日志。
- **禁止静默吞异常**：禁止空 `catch`、仅写“忽略异常”注释、仅返回默认值或仅打印到标准输出。需要忽略时，先记录至少 `warn` 级别日志，再执行原定处理；记录日志不改变原有失败、降级、重试或中断语义，也不要求为每次调用额外包一层 `try/catch`。

## Part B. 当前项目适配规则

### B1. 异常处理规范
- **业务异常**: 所有业务逻辑错误（如“金币不足”、“等级不够”）必须抛出 `LogicException` 或其子类。
- **推荐写法**: 使用 `player.fail(ErrorMsgEnum.xxx)`，它会自动抛出异常并中断流程，由最上层 Handler 捕获并返回错误码给客户端。
- **禁止写法**: 禁止在业务代码中捕获 `LogicException` 后“吞掉”异常，除非是为了做特殊的补偿逻辑。
- **日志记录**: 捕获未知异常时，日志必须包含 `exception.getMessage()` 和完整的堆栈信息。

### B2. 核心 API 使用规范
- **禁止静态导入**：本次新增或直接修改代码不使用 `import static`，常量和静态方法通过类名引用，保持来源可见；不为这一规则批量整顿未触达的历史测试。
- **时间获取**:
  - 禁止: `System.currentTimeMillis()`
  - 必须: `DateUtil.currentTimeMillis()` 或 `DateUtil.currentTimeSeconds()`
- **随机数**:
  - 必须: `cn.game.util.Rnd` 工具类
- **日志输出**:
  - 禁止: `System.out.println`
  - 必须: `log.info()`, `log.error()`, `log.debug()`
  - 要求: 尽量在日志中包含 `playerId` 以便追踪。

### B3. 资源操作规范 (PlayerHelper)
- **增加资源**: 使用 `PlayerHelper.addResources(player, itemId, count, OpType.XXX, true)`。
  - 参数说明：`notify` 控制既有资源通知；业务响应仍按协议契约显式填入返回的 `RewardInfo`，不要假设该参数会替 Handler 填充 Response。
- **扣除资源**: 使用 `PlayerHelper.delResources(player, costId, costNum, OpType.XXX)`。
  - 特性: 如果资源不足，该方法会自动抛出异常，无需手动 `if (count < need)` 检查。
- **检查资源**: 仅检查不扣除时，使用 `PlayerHelper.isEnough(...)`。
- **额外说明**: 增加资源和扣除资源时，重载的参数类型很多，这里没有完全列举出来，涵盖了各种类型的参数。

### B4. 注释规范
- **JavaDoc**: 所有 `public` 方法必须编写 JavaDoc，说明参数约束、返回值和可能抛出的异常。
- **行内注释**: 避免语法直译（如 `i++ // i加1`）；按 Part A 同时说明实际步骤目的与必要的设计原因。

### B5. 线程、分层与持久化

- 本项目采用 JDK 21、Maven、Handler / Module / Helper 与 Protobuf；详细入口见 [ai-coding.md](ai-coding.md)。
- 玩家对象只在所属队列修改；Handler / Manager 单例不保存请求级可变状态。异步操作使用 `AsyncUtils.await(...)`；外部回调先回投玩家队列。串行玩家队列不自动保证跨玩家或跨节点业务原子性。
- 常规 Module 由框架定时全量保存；`alwaysStoreDataInStandaloneTable()` 对应的独立表走 `DbEntity` 契约。确认保存完成后再做冷重载断言，不能把读取同一内存对象当作落库验证。
- 通用错误码先检查 `ErrorMsgEnum` 是否精确匹配；不同失败原因必须可辨识，不照搬其他项目的数值码或 JSON 失败响应格式。
- 批量消耗复用 `PlayerHelper.delResources` 的匹配重载，避免逐项循环扣除造成部分成功。奖励经 `PlayerHelper` 处理，返回值与通知各负其责。
- 时间统一走 `DateUtil`。默认按服务器自然日（00:00）跨天：`PlayerHelper.refreshDay` 使用 `DateUtil.getDay()` 并触发 `EventTypeEnum.NewDay`；自然日比较使用 `isSameDay` / `nextDayStartTime`。已有明确 05:00 业务日的功能沿用 `getDayCustom` / `isSameBusinessDay` 与 `NewDay5`，不得混用两套日标识或为套默认值改变旧规则。部署时区按服务器配置确认，不硬编码其他项目时区；新增活动窗口在功能规则中明确。
- 配置类和 Manager 是生成产物，不手工改生成结果来规避源配置问题。

### B6. 兼容、性能与维护经验

- 同一调用链复用已加载对象，先参数/内存/开关等低成本检查，再读存储或做重计算。
- 新增持久化字段优先增量扩展；兼容缺省值和旧记录，迁移必须幂等。明确新旧服务端是否并行写入、旧代码保存是否丢失新字段，必要时在兼容窗口内保留双写或等价回写。
- 发布顺序、客户端是否允许回退尚未在本项目确认；具体任务先核实，不能套用别的项目“服务端先滚更且客户端不回退”的前提。
- 查看他人数据时按接收方客户端能力过滤展示，存储保留真实值。缺失静态配置的 ID 使用协议约定的安全值或过滤列表，不改写拥有者的真实状态。
- 埋点、日志字段优先复用同语义约定；无既有约定且影响外部消费时，在相应需求/设计中确认，不临时自造同义名。
- 中文注释、捕获异常至少 warn 并传递异常对象的规则适用于本次新增或直接修改代码；历史示例中的机械编号不作为新增代码模板。
